# RapidTal Portal — Pre-Shareholder CTO Audit

**Date:** 2026-06-16 · **Auditor role:** CTO / product architect / technical auditor
**Method:** Full structural inventory + five parallel domain deep-dives (auth/security, CRM/tasks/SOPs, AI/vault/brain/tools/edge, notifications/email/my-job/admin, frontend), every claim grounded in `file:line` evidence. Two headline findings were personally re-verified and fixed during the audit.

> **Scoring legend (1–10):** 10 = shareholder-ready, scalable, production-grade · 8–9 = strong, needs polish · 6–7 = usable, not yet excellent · 4–5 = weak/incomplete/risky · 1–3 = broken/dangerous/rebuild. **Security column is a RISK score where 10 = lowest risk.**

---

## 1. Executive summary — the honest state of the product

RapidTal is **substantially more built, and more disciplined, than a typical pre-Series-A product.** The numbers: **55 pages, 109 API routes, 128 components, 79 migrations across 53 tables with 112 RLS policies, 9 Deno edge functions, 210 passing unit tests.** This is a real multi-tenant SaaS with three coherent personas (super_admin, client_admin, va), not a demo.

**What is genuinely strong (shareholder-ready or close):**
- **Security & multi-tenancy.** 100% RLS coverage as real defense-in-depth on top of in-code tenant scoping; `getUser()` (network-verified) everywhere including edge hops; AES-256-GCM credential vault with the key held outside Postgres; non-escalating impersonation with audit trail. **No Critical or High cross-tenant or privilege-escalation vulnerability exists.**
- **The Vault/RAG pipeline.** Genuinely hybrid retrieval (pgvector + FTS, merged/re-ranked, DNA-pinned), resumable self-healing ingestion, concise/deep modes that are materially different. Production-mature.
- **Tasks, Notebook, Access Credentials, Admin Health, AI Tools, Profile, Prompts manager** — all well-architected, several with unit-tested pure cores.
- **Engineering hygiene.** Token-only styling genuinely enforced (3-file grandfathered baseline), a real ui/ primitive set, error boundaries wired to a DB error log, consistent naming, a migration ledger with drift detection on `/admin/health`.

**What is weak or risky (must not be oversold to shareholders):**
- **A monthly-pay billing bug** (`lib/my-job/pay.ts`): invoices and **tax documents** bill a flat monthly fee independent of days worked — a full month and a single logged day bill identically. This is the single highest-business-risk defect.
- **The Brain "learning loop" is half-closed and silently degradable.** Three canonical `PROFILE_FIELDS` lists have drifted (the exact hazard CLAUDE.md warns about); memory injection is duplicated Next-side vs edge and isn't scope-filtered on Ask-the-Vault; decay/score-snapshots only run for clients who keep giving feedback; and an unset `OPENAI_API_KEY` silently disables dedup so memory rots while looking healthy.
- **Transactional email is wired to exactly one route** (login link). Leave approvals, issues, task assignments — nobody is emailed. For users who live outside the portal this is a product gap, not a bug.
- **Frontend has excellent shared patterns that almost nobody uses** — `useResource` (2 of 128 components), `ui/table` (1 of 6 table renderers), no shared `EmptyState` (41 hand-rolls), skeletons abandoned for spinners. Sound foundation, shallow adoption.
- **Operational silent-degradation risks** matching this codebase's own documented history (migrations 018–023 applied weeks late): edge deploy covered only 2 of 8 functions (**fixed in this audit**), in-memory rate limits that reset per serverless instance, and "next due/action date" reminder columns no cron ever consumes.

**Two findings were verified and fixed during this audit** (both small, both shipped):
1. **Restricted-SOP run-mode privacy bypass** — `/sops/[id]/run` omitted the `sop_access` grant check the detail page enforces; a same-tenant VA who knew a restricted SOP's id could open run mode and read its full body. Now gated identically. (Bounded: intra-tenant only; cross-tenant was always blocked.)
2. **Edge-deploy gap** — `deploy-functions.yml` deployed only `vault-ask` + `content-generate`; the other 6 functions could silently lag source. Now deploys all 8.

**Verdict:** The platform is **demo-ready and architecturally credible for a shareholder review today**, provided the narrative is honest. It is **not yet "press the button and scale to thousands of paying tenants" production-ready** — there is a short list of correctness and operational fixes (led by the pay bug) that should close before real revenue scale. See §18 for the readiness score and §22 for the must-fix-first list.

## 3. Admin feature audit

The admin surface is **complete — no stub or half-built pages exist** — and contains two standouts and a couple of scale cliffs.

- **Standouts:** `/admin/health` (migration-ledger drift, `health_schema_check()` incl. the Notebook-privacy invariant, cron heartbeats, both Brain env rows, per-client vault indexing, 24h errors) and the **Prompts manager** (slug-keyed admin overrides with a genuinely good variable-validation guard). Both keep/A-grade.
- **Scale cliffs to fix:** `admin/users` calls `listUsers({perPage:1000})` — **silently breaks past 1000 users** (the auth provider returns only the first page). `ClientsTable`/`UsersTable` are 600-line hand-rolled local-state components, **not** the `useResource` layer (CLAUDE.md incorrectly claims `useResource` "backs Users" — correct the doc or the code). `admin/placements` is N+1 (2 queries per placement) and carries a dead `"client"` role branch (no such role exists).
- **Cross-tenant gap:** `admin/daily-logs` is scoped to `user.client_id` only, so a super_admin sees **just one tenant with no client picker** — a functional gap for cross-tenant review.
- **Errors viewer** is the weakest admin page: a read-only 100-row dump with no filter/search/dedup/resolve-state — a single error loop buries everything. Needs triage (dismiss/resolve, dedup by hash, pagination).

## 4. User (VA) feature audit

The VA experience is the **most mature persona** (My-Job is the largest domain) but carries the **highest-business-risk bug**.

- **`lib/my-job/pay.ts` monthly-pay bug (High).** Monthly `pay_period` is a flat per-month fee independent of days worked; invoice and **tax** documents pass `monthsInPeriod=1`, so a full month and a single logged day bill identically. Hourly with zero logged hours silently invoices $0. Fix the proration before any of these documents are shown to a real VA or tax authority.
- **Leave (Medium):** no overlap/duplicate-request guard and no "already-reviewed" state guard — a declined→approved flip silently re-counts balance. Public holidays aren't excluded despite `holidays.ts` data + an `exclude` hook existing unwired; Dec→Jan leave mis-buckets to the start year.
- **Self-report is write-only** — `va_self_reports` has no admin reader, so its "performance paper trail" purpose isn't served. Either surface it in Supervision or remove it.
- **Dead code:** `MyJobHub.tsx` carries ~70 lines of unreachable admin path (`TeamLeaveTab`, `isAdmin`) — the real admin UI is `components/team/TeamLeaveApprovals.tsx`. Remove. Holiday data is hardcoded to 2026 (annual manual refresh).
- **Strong:** contract view, days/attendance, documents-as-real-PDF (server-rendered HTML → print), notebook, tools.

## 5. Client feature audit

The client home is **purpose-built and good** (request work → approve deliverables → see value/overdue/due-soon), and the new MoM report adds the context clients ask for first.

- **Discoverability gap (High):** the **task approval action lives only on the client dashboard**, not on `/tasks`. A client_admin on the board has no approve/request-changes affordance and will drag-to-done, bypassing the structured note + `task_approved` notification. Add approve/changes to the board's `TaskDialog` when `status==="review"`.
- **Three overlapping "brain health" surfaces** (`/brain`, `/brain-analytics`, `/company-report`) — consider merging to reduce client confusion and a duplicate sidebar entry.
- **Client_admins can't browse the SOP library** (redirected off `/sops`; reach SOPs only via Notebook/deep links) yet have edit/fork rights — reads as half-finished. Decide and document.

## 6. Candidate / VA experience

Covered in §4. The platform treats the VA as an *employee* (contract, leave, pay, documents, issues, daily logs) more than a *candidate* — there is **no applicant/ATS pipeline**; "candidate" in practice means a placed VA. If the business model includes recruiting/screening, that is a whole domain that does not yet exist and should be on the roadmap, not implied as built.

## 7. Authentication & permissions audit

**Score 8.5/10 — the strongest domain.** Full write-up in §12. No Critical/High. The deductions are operational: in-memory rate limiting (per-instance, bypassable across warm serverless instances — matters most for credential-reveal and login-link), a 30s stale-role window on warm instances (mitigated by `invalidateCachedIdentity`), and a minor cross-tenant *enumeration* (not write) in `team/[id]` where the role check precedes `assertClientAccess`.

## 8. Database & Supabase audit

- **Schema:** 53 tables across 79 numbered migrations with a self-recording `schema_migrations` ledger and a `manifest.ts` mirror guarded by a unit test — a genuinely good migration discipline, with `/admin/health` surfacing drift. **History lesson is real:** 018–023 were applied weeks late; the deploy/cron backstops now exist but the *operational* discipline (run the runner, check health) remains a human dependency.
- **RLS:** 112 policies, **100% table coverage**, no `USING(true)`/`anon` policies, recursion fixed via `SECURITY DEFINER` helpers with pinned `search_path`. Real defense-in-depth.
- **Data-modelling smells:** stale generated `types/database.ts` (forces `as any`/`as unknown` casts for `visibility`, `subcategory`, `deleted_at` — regenerate); `time_entries.category` is unconstrained free text and **collides in name** with `task_categories` (unrelated concept); SOP `version` is an int with **no history table** (drift is detected but the diff can't be viewed); `expenses.next_due_date` and `leads.next_action_date` are indexed but **no cron consumes them** (dead reminders).

## 9. Edge functions audit

**Score 8/10.** Eight uniformly well-structured Deno functions (consistent CORS, network-verified `getUser()`, role+tenant re-checks, graceful key-absence, error-to-DB write-back). `vault-process` (resumable embedding against the CPU-cap kill), `vault-delete` (cross-tenant verification before any delete), and `content-generate` (semantic retrieval + self-critique) are standouts. **The systemic risk is the Next↔Deno boundary**: edge functions can't import `lib/brain/context.ts`, so memory-injection logic is **duplicated** in `content-generate` and `vault-ask` and has already drifted (no scope filtering on the vault side). The **deploy gap (2 of 8) is fixed in this audit.** `vault-crawl` is **orphaned** (its only caller is the dead `/api/vault/crawl` route — delete both or wire them up).

## 10. Code modularity audit

**Bimodal.** Exemplary shared layers — `components/tools/shared.tsx` (backs all 17 tools), `lib/hooks/useResource.ts` + `useCrudDialog.ts`, the `lib/tasks/metrics.ts` pure-and-tested core, `lib/sops/sop-access.ts` — coexist with real duplication:
- **SOP scope-auth written 3×** (`authorizeScope`, `authorizeSopScope`, inline in `categories/route.ts`).
- **SOP AI `DEPTH_HINT`/`AUDIENCE_HINT` + step-sanitise duplicated** between `generate/route.ts` and `lib/sops/ai.ts`.
- **Vault SSE streaming duplicated ~95%** between `AskVaultClient.tsx` and `ComposeClient.tsx` (~100 lines) — extract `useStreamSSE()`.
- **Brain memory-injection duplicated** Next-side vs edge (§9).
- **Reports re-derive** hours/on-time math inline instead of `lib/tasks/metrics.ts` (a documented CLAUDE.md rule).

## 11. Frontend architecture audit

**Score 6/10 — sound foundation, shallow adoption.** Real ui/ primitives on base-ui+cva, token discipline genuinely enforced (3-file baseline), React Query app-wide, error boundaries → `app_errors`, consistent naming. But: `useResource` used in **2 of 128** components; **14 components use raw `fetch()`** bypassing the toast layer; **3 silently swallow errors** (`LeadsBoard`, `MessagesClient`, `RevisionDrawer` — `.catch(()=>{})`); **no shared `EmptyState`** (41 hand-rolls); skeletons abandoned (`animate-spin` in 72 files, `Skeleton` in 1); `ui/table` adopted by 1 of 6 table renderers; `ComposeClient.tsx` is a 612-line/15-useState monolith; a dead duplicate `lib/query-provider.tsx`; orphan components (`RoleBadge`, `SopNewForm`, possibly `VaultList`). No `<Suspense>` anywhere; 48/55 pages `force-dynamic` + client fetch, so the App Router streaming model is unused. **This is migration work, not redesign.**

## 13. UX & design consistency audit

Design-system consistency **8/10** (real primitives + enforced tokens, but `ui/table`/`Skeleton`/`ui/dialog` under-adopted). Error/loading/empty **5/10** (boundaries right; spinner monoculture, 41 ad-hoc empty states, 3 silent error swallows). ## 14. Error handling audit

Strong infrastructure (`lib/error-tracking.ts` → `app_errors`, rate-capped, never throws; React boundaries report via `lib/report-client-error.ts`), undermined by **3 silent `.catch(()=>{})`** swallows and **several fire-and-forget inserts that only `console.warn`** (CRM events, lead stage events, Notebook reorder returns `{ok:true}` without checking N updates → latent inconsistency). Convert silent catches to either captured errors or visible toasts; check `Promise.all` results on multi-write reorder paths.

## 15. Scalability audit

Tenant-scoped queries + indexes are generally sound, but there are concrete **silent-truncation cliffs**: `CrmBoard` client-side filters a hard `limit(500)`; daily-log all-VA aggregate `limit(500)`; `listUsers(perPage:1000)`; `/admin/health` loads **all** `vault_items`+`chunks` into Node (ironic vs migration 062's SQL-aggregation pattern). None break today at small tenant counts; all will silently lose data at scale and should move to server-side pagination / SQL aggregation before scale-up. Rate limiting must move off in-memory before multi-instance scale.

## 16. Performance audit

No egregious hot paths. Watch items: N+1 in `admin/placements` (2 queries/placement) and the Clients/Users delete loops (sequential `await` over `auth.users`); SOP `reorder` does up to 500 sequential updates with no transaction (partial-failure inconsistency); tools `calendar`/`repurposer` routinely truncate generation mid-array (root fix: chunked generation, not `json-salvage`). 48/55 pages `force-dynamic` means little static caching — acceptable for an authed app, but no ISR/edge-cache wins are being taken.

## 17. Backend architecture audit

The `withAuth`/`withSuperAdmin` + `assertClientAccess` + Zod pattern is good and **near-universally applied**; the exceptions are the thin edge proxies (which delegate auth to network-verified edge `getUser()`) and a couple of routes missing wrappers (`company-dna/scrape` has **no auth wrapper and no Zod**, unlike every sibling — fix). The `ROUTES` registry and `api-client` give a typed client→server contract where adopted. The main backend weakness is the **Next↔Deno duplication** and a few routes that still build prompts inline instead of via the prompts registry.
