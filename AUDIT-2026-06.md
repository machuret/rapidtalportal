## Role model & VA access (resolved)

The system has three roles (`types/database.ts`): **`super_admin`** (platform Admin, no
tenant), **`client_admin`** (the "Client" — owns one tenant), and **`va`** (a Virtual
Assistant assigned to a tenant). Relationship: `super_admin` creates clients and all users;
`client_admin` manages the VAs in its own client; a `va` belongs to one client and acts
within it. Tenant isolation is enforced in the API layer via `assertClientAccess`
(the DB is accessed through the service-role client, which bypasses RLS).

An earlier review flagged that several client-scoped features were hidden from VAs in the
sidebar but left open at the API (tenant-scoped only). The intended model is that **VAs may
use these within their own client**, so the UI was aligned to the (already-correct) API
rather than locking the API down. Current matrix:

| Feature | super_admin | client_admin | va |
|---|---|---|---|
| Clients / All Users / per-client user mgmt | ✅ | — | — |
| My Team (view/edit VA profiles) | ✅ | ✅ | — |
| Daily Log — own | — | ✅ (+backfill) | ✅ (today only) |
| Daily Log — review others + feedback | ✅ | ✅ | — |
| Messages (Client ⇄ VA) | — | ✅ | ✅ |
| Knowledge Base — view | — | ✅ | ✅ |
| Knowledge Base — regenerate / edit entries | ✅ | ✅ | — |
| CRM (contacts & notes) | ✅ | ✅ | ✅ |
| Content — create drafts/topics | ✅ | ✅ | ✅ |
| Content — approve/reject/delete | ✅ | ✅ | — |
| Company DNA — view & **edit** | ✅ | ✅ | ✅ |
| Vault — add/edit/reprocess | ✅ | ✅ | ✅ |
| SOPs — view | — | ✅ | ✅ |
| SOPs — create/edit/delete | ✅ | ✅ | — |

Net: a **VA now has the same menu as a Client minus "My Team"** and minus the
approval/management powers (content approval, KB regeneration, SOP authoring, daily-log
feedback), all of which remain gated to `client_admin`/`super_admin`.

## High severity

### 1. `Cache-Control: public` on every API route

`next.config.mjs`:

```js
async headers() {
  return [{
    source: '/api/(.*)',
    headers: [{ key: 'Cache-Control', value: 'public, max-age=300, stale-while-revalidate=600' }],
  }, ...];
}
```

This header is attached to **every** API response, including authenticated, per-user GETs such as `/api/crm/contacts`, `/api/profile`, `/api/time-entries`, and `/api/daily-log/*`. The `public` directive permits **shared caches** (the platform CDN, corporate proxies) to store the response and serve it to a *different* user. At minimum, `max-age=300` means a user can be served another user's data for up to 5 minutes after a cache fill.

**Recommendation:** Default API responses to `private, no-store` and opt specific, non-personalized endpoints into caching explicitly. Either remove this blanket rule or scope it:

```js
{ source: '/api/(.*)', headers: [{ key: 'Cache-Control', value: 'private, no-store' }] }
```

Apply caching per-route via `NextResponse` headers only where the payload is non-sensitive.

## Medium severity

### 2. TanStack Query is installed and provided app-wide but barely used

`lib/query-provider.tsx` mounts `QueryClientProvider` (good config: `staleTime`, `gcTime`, `retry`, `refetchOnWindowFocus: false`) around the whole portal, yet only **`components/content/ContentStudio.tsx`** calls `useQuery`/`useMutation`. The other ~15 client components fetch through `lib/api-client.ts` (`apiClient` + manual `useEffect`/`useState`).

The result is **two data-fetching paradigms** living side by side and the caching/dedup/retry benefits of React Query going unrealized everywhere except one screen.

**Recommendation:** Pick one. Either (a) migrate the manual `useEffect`+`apiClient` fetches onto React Query (keep `apiClient` as the `queryFn` transport), gaining caching/dedup for free; or (b) drop `@tanstack/react-query` + devtools entirely and standardize on `apiClient`. Option (a) is the higher-value path given the provider is already wired up.

### 3. Dead, duplicated cache modules

`lib/cache.ts` (258 lines) and `lib/cache-improved.ts` (262 lines) are near-identical — same `SimpleCache`, same `CacheManager`, `RetryManager`, `ContentValidator`, same cache-key map. The only differences: `cache-improved.ts` makes the methods `async` and adds a `rateLimit` key + `healthCheck()`.

Neither is imported anywhere in `app/`, `components/`, or `lib/` — the **only** reference is `__tests__/cache.test.ts`. This is ~510 lines of dead, divergent code plus a test suite validating code nothing ships.

**Recommendation:** Delete both modules (and the test) unless caching is wired into the scrape/KB paths. If a cache is wanted, keep one implementation and actually call it — see #4.

### 4. In-memory cache is ineffective on serverless

Both cache modules instantiate a module-level `new SimpleCache()` backed by a `Map` with a `setInterval` cleanup, and register `process.on('SIGTERM'/'SIGINT')` handlers. On a serverless/edge deployment (the apparent target — Supabase Edge Functions + Next on Vercel):

- The `Map` is **per-instance** and discarded between cold starts; cache hit rate trends to zero under typical autoscaling.
- `setInterval` and `process.on(...)` are anti-patterns in serverless functions (no long-lived process; can keep instances warm or leak).

The comments even say *"In production, replace with Redis or similar"* — that replacement never happened.

**Recommendation:** If caching is needed (scraped pages, OpenAI extractions), use a shared store: Supabase table with TTL column, Upstash Redis, or the platform data cache. Otherwise remove (#3).

### 5. `tsconfig.json` excludes tests and seeds from type-checking

```json
"exclude": ["node_modules", "db/seed.ts", "db/seed.mjs", "supabase/functions", "__tests__"]
```

The prior analysis doc reported "136 TypeScript errors in test files." Those were resolved by **excluding the files from compilation**, not by fixing them — so `next build`/`tsc` no longer sees them and the errors can silently rot. (`supabase/functions` is reasonably excluded since it's Deno; tests are not.)

**Recommendation:** Remove `__tests__` from `exclude`, add proper Jest/node types so tests type-check, and let CI catch regressions. Keep Deno edge functions on their own `tsconfig` (they already have `supabase/functions/tsconfig.json`).

### 6. Jest module alias is silently broken

`jest.config.js`:

```js
moduleNameMapping: { '^@/(.*)$': '<rootDir>/$1' }   // ← wrong key
```

The Jest option is **`moduleNameMapper`**. As written, the `@/...` alias mapping is ignored. Tests currently pass only because the two existing test files don't exercise the alias in a way that breaks; any new test importing `@/lib/...` may resolve via `next/jest`'s built-in mapping or fail. Combined with `coverageThreshold.global = 70%` and only **two** test files, running `jest --coverage` over the configured `collectCoverageFrom` (`lib/**`, `app/api/**`) would fail the gate.

**Recommendation:** Rename to `moduleNameMapper`; either lower the coverage threshold to a realistic starting value or add tests before enforcing 70%.

## Low severity

### 7. Two auth helpers
`lib/auth.ts` (`getCurrentUserAndClient`, `requireRole`) serves Server Components and is nicely wrapped in `React.cache()` to dedupe the user+client lookup across layout+page. `lib/api-auth.ts` (`requireApiAuth`, `assertClientAccess`) serves route handlers. Both re-query the `users` table per request. This is fine functionally, but the split isn't documented and both carry the same `TODO` about moving role/client_id into JWT claims to drop the per-request DB lookup.

**Recommendation:** Add a short comment cross-referencing the two, and pursue the JWT-claims optimization both files already describe — it removes one DB round-trip from every authenticated request.

### 8. Dependency / bundle nits
- `@tanstack/react-query-devtools` is a **production** dependency and `<ReactQueryDevtools/>` is rendered unconditionally in `QueryProvider`. The package no-ops in production builds, but it's still installed and worth gating behind `process.env.NODE_ENV === 'development'` (and moving to `devDependencies`) for clarity.
- Two major versions of **zod** resolve in the lockfile: `zod@4.4.2` (your direct dep) and `zod@3.25.76` (transitive). Both can ship. Not a bug, but a bundle-size/consistency note.
- `undici` is a devDependency that exists only for the stray root script (#9); Node 18+ has global `fetch`.

### 9. Repo hygiene
- `test-web-scraping.js` at the repo root is an ad-hoc manual script, referenced by nothing — move to `scripts/` or delete.
- `35` `console.*` calls across `app/lib/components`. The Server Component error logging (e.g. `dashboard/page.tsx`) is reasonable, but consider a thin logger so output can be silenced/structured in production.
- `CODE_QUALITY_ANALYSIS.md` is now partially inaccurate (claims missing error boundaries — `app/error.tsx` and `app/(portal)/error.tsx` exist; claims `<img>` usage — none found). Either update or remove to avoid misleading future readers.

## What's genuinely good (keep doing this)

- **Server-side data fetching is well done.** `dashboard/page.tsx` runs 5 queries via `Promise.all`, checks each error, and passes typed results down — no client waterfalls. `force-dynamic` + `React.cache()` in `lib/auth.ts` dedupes the user lookup across the render tree.
- **Auth verification is correct.** `lib/edge-proxy.ts` and `lib/api-auth.ts` use `getUser()` (network-verified JWT) rather than `getSession()` for identity, with a clear comment explaining why. The proxy routes that *look* unauthenticated are in fact authenticated inside `proxyToEdgeFunction`.
- **Error response shape is consistent** — ~146 `{ error }` responses vs. only 9 `{ success }`, so clients can rely on `error`.
- **Indexing was considered.** `db/migrations/016_missing_indexes.sql` adds composite indexes that match the actual query filters/sorts (e.g. `time_entries(user_id, work_date, started_at)`), with comments explaining each.
- **`api-client.ts`** is a solid fetch wrapper: typed `ApiError`, exponential backoff, no-retry on 4xx (except 429), 204 handling.

## Suggested order of work

1. **Fix #1** (API cache header) — small change, removes a real cross-user exposure risk.
2. **Resolve the data layer (#2)** — commit to React Query or remove it; stops the architecture from drifting further.
3. **Delete dead cache code (#3/#4)** or replace with a shared store if caching is actually wanted.
4. **Fix the test config (#5/#6)** so `tsc` and `jest` actually guard the codebase, then start raising coverage.
5. **Housekeeping (#7–#9)** as you touch the relevant files.

*Architecture note (#10):* every DB read/write goes through the service-role admin client, so Postgres **RLS is not the enforcement boundary** — application code is. That's a valid model, but it means a single missing `assertClientAccess`/role check in a route handler is a tenant-isolation bug with no database backstop. A defense-in-depth pass on RLS would be worth a dedicated **security** audit (out of scope here, per the selected focus).
